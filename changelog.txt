== Changelog ==

Every change to WP Plugin Starter. readme.txt lists the latest version in short.

= Unreleased =
* New: screenshots at the top of README.md on GitHub and in readme.txt → Screenshots, saved as .wordpress-org/screenshot-N.png (WordPress.org's assets/ names; not in the release zip).
* Developers: the Read Me tab leaves out anything between <!-- github-only:start --> and <!-- github-only:end -->, like the badges block, for parts of README.md that only make sense on GitHub.
* Developers: scripts/rename-plugin.sh no longer adds a CodeFactor badge to a new plugin's README. CodeFactor serves a badge only once the repository is added on codefactor.io, so it showed as a broken image on GitHub. DEVELOPMENT.md → Services setup has a new step 3 for CodeFactor, with the badge to add afterwards. Nothing changes for users.

= 1.0.12 =
* Fixed: Updates from GitHub reads the last Location header when GitHub sends more than one, instead of the text "Array" and a PHP warning, when it looks up the latest release and a private release's download.
* Fixed: the settings screen's styles and script are versioned by their file times as text, falling back to the plugin version when a file time can't be read; empty script handles from the wpstarter_admin_script_deps filter are dropped.
* Fixed: the Read Me tab, release notes, line lists and domain lists no longer fail on text that a regular expression can't split; they are treated as empty.
* Developers: PHPStan runs at level 7 (phpstan.neon.dist), without the missingType.* checks, which ask for types on every parameter, return, property and array. Plugins made from the starter fix their own level-7 findings, or note stub mistakes in phpstan-plugin.neon, before syncing phpstan.neon.dist.

= 1.0.11 =
* Developers: new core workflow .github/workflows/release.yml. Pushing a vX.Y.Z tag on main checks the tag is on main, runs scripts/preflight-release.sh on it, builds the zips from it with scripts/build-release.sh and publishes the GitHub release with {slug}-X.Y.Z.zip, its notes taken from the version's section of the README.md changelog. In a public repository it signs the zip's SLSA build provenance with Sigstore (actions/attest-build-provenance) and attaches the bundle as provenance-{slug}-X.Y.Z.sigstore.json, a name that does not start with the slug so Git Updater never installs it; OpenSSF Scorecard counts it for Signed-Releases. Private repositories get the release without provenance, as attestations there need GitHub Enterprise Cloud. RELEASING.md step 3 is now tag and push; publishing by hand stays as the fallback, and a re-run of the workflow replaces a hand-built zip with its signed build.
* Developers: scripts/update-test.sh accepts the provenance bundle next to {slug}-X.Y.Z.zip and checks it with gh attestation verify against the zip, the Release workflow and the tag; any other asset still fails the test. Nothing changes for users.

= 1.0.10 =
* Changed: the README's Built with AI section (the Read Me tab) says the plugin works well with SEO Pro Stack, the wpallstars base plugin for speed and an organised admin. readme.txt and the plugin's screens don't mention it.
* Developers: every plugin except SEO Pro Stack keeps that line in README.md only (STANDARDS.md → Structure), and scripts/preflight-release.sh warns when it is missing or gets into readme.txt. DEVELOPMENT.md → Test site resources: every test site runs SEO Pro Stack.
* Developers: new core workflow .github/workflows/scorecard.yml runs OpenSSF Scorecard on pushes to main, every Monday, on branch protection changes and by hand, uploads the results to code scanning and publishes them for the Scorecard badge. It needs no setup and is skipped in private repositories. DEVELOPMENT.md → Checks → Scorecard; the public launch sweep runs it once and adds its badge.
* Developers: new core file CODE_OF_CONDUCT.md (Contributor Covenant 2.0, from GitHub's API), with reports going privately to the contact in SECURITY.md. CONTRIBUTING.md links it; .distignore and scripts/preflight-release.sh keep it out of both release zips. Nothing changes for users.

= 1.0.9 =
* Developers: STANDARDS.md has a Performance section every plugin made from the starter follows: load only what is used, no full table scans (no unlimited queries, no lookups or sorting by meta_value, LIKE '%term%', REGEXP or ORDER BY RAND() on large tables, no_found_rows unless a total is shown, indexes on the plugin's own tables but never on WordPress's), one autoloaded settings array, caching with wp_cache_* and transients, bulk work in batches through cron, no request on every page view, and measuring on large data. Code rules add "WordPress first": core APIs before custom code, PHPCS findings fixed in the code.
* Developers: PHPCS adds the performance sniffs of WordPress VIP's standard (automattic/vipwpcs, the WordPressVIPMinimum.Performance group only): unlimited queries, ORDER BY RAND(), REGEXP, post__not_in, cache times under five minutes and remote request timeouts over 3 seconds fail the lint. Plugins made from the starter need `composer update` after syncing composer.json.
* Developers: scripts/smoke-test.sh seeds 10,000 posts with three meta rows each (--posts N), lists every request's query count and time, and runs EXPLAIN on the plugin's own queries: a full table or index scan, or a sort without an index, over 1,000 rows or more fails. A canary query proves the check works. The recorder is scripts/smoke-queries.php, a new core file.
* Developers: scripts/update-test.sh no longer fails the WP-CLI update check with WPALLSTARS_GITHUB_TOKEN set. With a token, the shared updater offers the release asset's API address (api.github.com/repos/{owner}/{repo}/releases/assets/{id}), which private repositories need; the test now accepts exactly that asset's address, read with gh, as well as the public {slug}-X.Y.Z.zip address. Nothing changes for users.

= 1.0.8 =
* Changed: the Built with AI section in README.md (the Read Me tab) and readme.txt sends questions to aidevops, which reads the plugin's docs and code to answer, and credits the starter with a "Made from WP Plugin Starter" line; readme.txt gets a "Where do I get help?" answer, and the Read Me's Report a problem paragraph points to aidevops for questions.
* Developers: every plugin made from the starter keeps both credits (STANDARDS.md → Structure). scripts/rename-plugin.sh writes the starter's "Made from" line for a new plugin after renaming, and scripts/preflight-release.sh warns when README.md or readme.txt lacks the aidevops credit or the "Made from" line. DEVELOPMENT.md → Set up recommends aidevops for development, the sites the plugins run on and questions; the docs still work with any AI tool or by hand.
* Developers: new core script scripts/update-test.sh for RELEASING.md step 4. It installs the previous GitHub release on a disposable WordPress in Docker and checks that the new release has exactly one asset, that WordPress offers it from that asset (WP-CLI, Check again on the Updates screen, the Plugins screen), that the update installs and the plugin stays active with no further update offered, that the settings screen loads and that debug.log stays empty; then it removes the site. --from and --to pick the releases (default: the newest two). For a private repository it reads releases with gh and passes WPALLSTARS_GITHUB_TOKEN to the test site from the environment, never on a command line or in a file. Nothing changes for users.
* Developers: the scripts pass text to grep -q and to awk that stops early as a here-string, not through a pipe. With pipefail, a writer cut off by SIGPIPE failed checks that matched once the text was over 64 KB, so scripts/preflight-release.sh sometimes said a large changelog.txt had no entry for the version. Nothing changes for users.

= 1.0.7 =
* Developers: DEVELOPMENT.md → Services setup: the once-per-repository steps for a new plugin, each with a check: SonarCloud (import with the project key {owner}_{repo}, Automatic Analysis off, SONAR_TOKEN), Codacy (Manage repositories → Add, then the README badge), SYNC_PAT for repo-metrics once main is protected, and one Starter sync run. It says which steps wait for public launch in a private repository (Codacy and branch rulesets need paid plans; SonarCloud's free plan covers private projects up to 50,000 lines per organization). DEVELOPMENT.md → SonarCloud points to it. Agents list these steps for the owner instead of doing them.
* Developers: STANDARDS.md → Agent docs: agents keep a plugin at the starter's standard. They check for an open starter-sync issue before work, read the starter's copy of any core file or rule the task touches while one is open, never change a core file only in the plugin (a change every plugin needs goes to the starter first), and leave account and secret steps to the owner. scripts/preflight-release.sh warns when AGENTS.md does not name STANDARDS.md. Nothing changes for users.

= 1.0.6 =
* Developers: SonarCloud runs from GitHub Actions (.github/workflows/sonarcloud.yml) with the new core file sonar-project.properties, which ignores the four rules WordPress coding standards contradict (php:S100, S101, S116, S1142). Automatic analysis ignored such settings, and the free plan has no per-project Quality Profile. DEVELOPMENT.md → SonarCloud lists the setup for a new plugin. Nothing changes for users.
* Developers: the Read Me tab's Markdown reader, the settings page navigation, the Plugins screen's replaced-plugin states and scripts/replaced-plugins.php are split into smaller methods; the admin CSS and JS paths are class constants. Their output is unchanged (compared before and after on every Markdown file in the plugin, six settings page states and 192 replaced-plugin cases). phpstan.neon.dist no longer needs its ignore for the Read Me reader's by-reference closure. sonar-project.properties ignores the findings that are by design, each with its reason and scoped to its files: unused parameters of the map-dispatched renderers and sanitizers, the method count of the settings store and the updater, role="switch" on a native checkbox, role="status" and role="group". It also leaves coverage out (sonar.coverage.exclusions): plugins are tested on a real WordPress by scripts/smoke-test.sh, so the default Quality Gate no longer fails every pull request on 0% coverage. Nothing changes for users.
* Developers: new core workflow .github/workflows/starter-sync.yml. Every Monday it compares a plugin's core files with the starter's (the starter's own scripts/sync-core.sh --check) and keeps one issue labelled starter-sync open while any differ, with the files and the steps to sync; it closes the issue once they match. No setup; the repository variable STARTER_REPO follows another starter. It does nothing in the starter. STANDARDS.md → Structure and DEVELOPMENT.md → Starter sync describe it. Nothing changes for users.

= 1.0.5 =
* Developers: scripts/preflight-release.sh treats only docs/{topic}.md as agent docs, so generated files in docs/metrics/ need no line in AGENTS.md. Nothing changes for users.
* Developers: new core file .codacy.yml: Codacy skips the generated composer.lock. It does not ship in a zip. Nothing changes for users.
* Fixed: "Select all" and "Clear" on a long list of choices find the list by id, so they also work for a setting whose key holds a dot or other character that means something in a CSS selector.
* Developers: the Bash scripts use [[ ]] for tests, every case has a default, and plugin-check.sh and smoke-test.sh read option values into a named variable. Behaviour is unchanged. Nothing changes for users.
* Developers: the settings screen renders each kind of child setting (select, multi, url, times, int, lines and domains, media, bool, text) in its own method, chosen from a map, instead of one long switch. The page's HTML, hooks and wps-* classes are unchanged. Nothing changes for users.
* Developers: scripts/rename-plugin.sh takes plugin names with quotes, $ and & (such as Owner's "Best" Plugin): the new name is escaped for where it lands (PHP strings, JSON, XML), and the renamed PHP is checked with php -l. Names with / \ < > % or control characters, and URLs with quotes or \, are refused before any file changes. scripts/sync-core.sh escapes the same way. scripts/replaced-plugins.php quotes the name in its README pattern. README.md's languages badge has a line of its own. Nothing changes for users.
* Developers: README.md shows badges on GitHub (CI, SonarCloud, Codacy, CodeFactor, license, latest release) and repository facts (lines of code, languages, dependencies) that .github/workflows/repo-metrics.yml keeps up to date in docs/metrics/. The Read Me tab leaves out the badges block and HTML comments, so it still loads nothing from other sites. scripts/rename-plugin.sh rebuilds the badges for the new repository. Nothing changes for users.
* Fixed: two settings saved at the same moment (two tabs, or two admins) could undo each other, as each save wrote back the whole settings array. A save now holds a short lock while it reads and writes. In a test of 20 saves at once, all 20 are kept (before, 4 to 9 were lost). Uninstalling also removes the lock's row, if one was left.
* Developers: the settings store's sanitize_value() hands each field type to its own small sanitizer, and search() and parse_times() are split into helpers. Values, signatures and option keys are unchanged.
* Developers: scripts/smoke-test.sh keeps its local-only HTTP install command on one line, so SonarCloud reads its NOSONAR note. Nothing changes for users.
* Fixed: a site on the GitHub build could be offered an unrelated WordPress.org plugin that has the same folder name. The GitHub zip's main file now carries an Update URI header on github.com (added by scripts/build-release.sh; the WordPress.org zip has none), and the updater (1.1.0) never takes WordPress.org's answer for such a build.
* Fixed: when GitHub did not answer for a release's requirements (Requires at least, Requires PHP), the release was offered without them for 12 hours; now the check fails and is tried again within the hour.
* Fixed: with a token, the updater took the first zip whose name started with the plugin folder; it now takes only {folder}-{version}.zip, as without a token.
* Fixed: a failed private download address is asked for once per update, its error is kept, and only an https address on a GitHub download host is used.
* Developers: the updater's repeated addresses and version pattern are constants, and its longest methods are split into smaller ones. Its filters and behaviour are unchanged; wpallstars_github_plugins entries may carry 'github_only'.
* Developers: scripts report failures instead of success. smoke-test.sh fails a page the site did not answer and never reads the previous page; sync-core.sh stops when the starter's core file list cannot be read, is empty, or names a folder with no files; plugin-check.sh fails when Plugin Check exits with an error but reports none; preview-site.sh takes over a lock only when its run's process has gone, never by age, so a run that takes over 10 minutes keeps it. DEVELOPMENT.md: CodeQL covers JavaScript and GitHub Actions, not PHP. Nothing changes for users.

Before, a new plugin kept the starter's version and changelog.

= 1.0.3 =
* Developers: scripts/rename-plugin.sh takes --description, --author, --author-uri, --plugin-uri, --contributors and --donate, so a plugin made from the starter carries its maker's details instead of the starter's. Each is optional; left out, the starter's value stays. Nothing changes for users.

= 1.0.2 =
* Developers: new Agent docs section in STANDARDS.md. AGENTS.md, which AI agents read in every session, stays a short map: the plugin's names, its own standing rules and one line per doc saying when to read it. Guidance for one kind of task goes in docs/{topic}.md, which never ships. The same pattern fits a small plugin and a large one. scripts/preflight-release.sh warns when AGENTS.md is over 150 lines, names a doc that does not exist, or leaves out one in docs/, and fails if docs/ gets into a release zip. Nothing changes for users.

= 1.0.1 =
* Fix: a select or multi-select setting whose options list fails (its callback throws, for example when another plugin's tables are missing) no longer stops every page after an update. That list is treated as empty, so the settings upgrade finishes; open fields keep their saved values and closed fields fall back to their default.
* Fix: scripts/sync-core.sh in a plugin made from the starter looks for the starter in wp-plugin-starter-template-for-ai-coding next to it again; renaming the plugin had renamed that folder name too, so it only worked with --from.
* Fix: release zips leave out DESIGN.md.
* Fix: the shared GitHub updater (copy 1.0.1) could not update from private repositories on sites where another plugin raises every request's redirection count (HTTP Requests Manager in a blocking mode sets it to 1): GitHub's redirect was followed, so the signed download address was lost and the token went along to the download host. Its requests to GitHub now never follow redirects, whatever other plugins set. Public repositories' release checks had the same problem.
* Fix: the shared GitHub updater's private downloads survive updaters that reset upgrader_pre_download (GPLVault Updater).
* Fix: a replaced plugin's Deactivate link on the settings screen did nothing on sites with Freesoul Deactivate Plugins: it saves its own copy of the active plugins list over any change not made from the Plugins screen. The link now checks the change was saved and, if not, saves just that change. Other code can use the same check: WPStarter_Replaced_Plugins::save_plugin_state().

= 1.0.0 =
* A fresh start, made from the parts every wpallstars plugin needs, taken from plugins in daily use: the settings screen with search, the Read Me tab, features as classes, replaced plugins, the shared GitHub updater, the release and check scripts, CI and the shared rules (STANDARDS.md, DEVELOPMENT.md, RELEASING.md). Earlier versions of this starter are retired; start again from this one.
* New: scripts/rename-plugin.sh gives a copy of the starter its own names, and scripts/sync-core.sh keeps a plugin's core files the same as the starter's.
